# Accessibility

Fudehand's own interface — the launch window, the editor, its panels, and the canvas — should be usable with the keyboard and VoiceOver and should respect the system's accessibility preferences (issue #174). Making the designs people draw accessible (for example checking their contrast) is a separate product feature and not covered here.

## Conventions

- **Labels**: every control that shows only an icon has an `.accessibilityLabel(L("…"))`, worded like its `.help` tooltip but without the shortcut ("Zoom In", not "Zoom In (⌘+)"). A label that names a layer includes it ("Lock %@"). Labels are UI copy, so each one has an entry in all four `Localizable.strings` tables and uses the terms in `GLOSSARY.md`. So does each image segment of a segmented `Picker` ("Left", "Vertical"). A toolbar menu takes its accessibility title from its image, so build that image with `NSImage(systemSymbolName:accessibilityDescription:)` and the localized label (the Appearance menu). A status shown only as a shape or color (the conversation tab's busy dot, the context-usage ring) gets a label too, and a value when it has one.
- **Click targets**: an icon-only button or menu is at least 16×16 points to click. Wrap its image in `iconHitTarget()` (at least 20×20, with the whole rectangle clickable) or give it an explicit `.frame(width:height:)` of at least 16×16. An icon-only `.borderlessButton` menu is drawn by AppKit at the height of its label image, ignoring SwiftUI frames, padding, fonts, and control sizes (a plain symbol gives 15 points): use `MenuIcon(symbol:label:)` as its label, which centers the symbol in a 20×20 template image described with the label. Toolbar items are sized by the system. Glyphs for close (`xmark`) and disclosure (`chevron`) controls are at least 10 pt.
- **Colors**: use system semantic colors (`.primary`, `.secondary`, `Color.accentColor`, `NSColor.windowBackgroundColor`, …) so light, dark, and Increase Contrast appearances follow the system; avoid fixed colors for text and controls.
- **Motion**: interface animations that only move the view honor *Reduce motion* (`NSWorkspace.shared.accessibilityDisplayShouldReduceMotion`) by jumping to their end. The canvas's viewport transitions (Fit All, Zoom to Selection, focusing a frame, the zoom buttons) do this. Playing a prototype or previewing a layer animation shows the design as authored and is not affected.
- **Canvas**: the canvas is a VoiceOver *layout area* labeled "Design canvas". Its children are the visible top-level layers in document order followed by any selected nested layers (a selected layer is listed even when hidden); each reads its layer name with the layer type as its role ("Home, Frame"), is positioned where the layer is on screen, and reports whether it is selected. Pressing one (VO-Space) selects that layer as a click would, and pointing at a layer finds its element (or its top-level layer's). The canvas posts selection and layout changes so VoiceOver follows panning, zooming, and edits. Editing goes through the layers and inspector panels, which are ordinary SwiftUI controls. The rules live in `FudehandCore/CanvasAccessibility.swift`.

## Checks

- `AccessibilityTests` (Swift) scans `Sources/FudehandApp` for icon-only buttons and menus (a label closure that holds only an `Image`) and fails when one has no `.accessibilityLabel` or a click target under 16×16. It does not see icon-only controls written another way (segmented `Picker` images, `Toggle(isOn:) { Image }`, `Label(…).labelStyle(.iconOnly)`), so review those by hand. `LocalizationTests` already fails on an `L("…")` call without a table entry.
- `CanvasAccessibilityTests` and the canvas tests cover the canvas's VoiceOver children and Reduce motion.
- Before merging a UI change, look at it with VoiceOver (⌘F5) and Accessibility Inspector (Xcode › Open Developer Tool) where it adds controls, and in light, dark, and Increase Contrast appearances.
