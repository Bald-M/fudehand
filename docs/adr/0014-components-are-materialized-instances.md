# Components Are Materialized Instances Kept in Step by the Editor

2026-11-24 (#256, step 1). Status: **accepted**. The design is in the [components spec](../superpowers/specs/2026-11-24-components-design.md); variants and component sets are step 2 and get their own decision.

A part that repeats across screens — a header, a tab bar, a button — could only be reused by copy and paste, and copies have no link to their original, so changing the header meant editing every copy. Fudehand now has **main components** and **instances**: a person or an Agent edits the main component once and every instance follows, while each instance keeps its own **overrides** (its text, colors, visibility, and other properties it changed).

## Decisions

- **An instance is an ordinary subtree of layers in the design document.** Its layers have ids of their own; the instance root records the main component it comes from (`instance`), each of its layers the main component layer it mirrors (`source`) and the property paths it overrides (`overrides`). The main component carries `component: true`. Rendering, `DesignIndex`, hit testing, layout, snapshots, the prototype window, and HTML export see ordinary layers and did not change.
- **The editor keeps instances in step, inside the edit.** `ComponentSync.reconcile(old:new:)` runs in `DesignEditor.perform` and `applyLive`, after the change and before annotation pruning and layout. It first turns every property an edit changed on a layer inside an instance into an override (or removes the override when the new value equals the main component's), so the canvas, the properties panel, and `design_update_node` need not know about components; it then rebuilds every instance whose main component changed: properties that are not overrides are copied, children are matched by `source`, layers new in the main component get fresh ids, layers gone from it are removed, and order follows it. A main component holding instances of another is synced after it. The main component's edit and its effect on instances are one undo step, and appear in the same frame during a drag. Undo and redo restore whole documents and need no reconcile.
- **Unchanged subtrees cost nothing.** Reconcile walks old and new together and descends only where they differ, which is cheap because unchanged child arrays share storage. A document without components does no measurable extra work per edit (`pnpm bench:native`, which also measures a drag inside a main component with 50 instances).
- **Override paths are the layer's JSON keys.** A top-level key (`fill`, `visible`, `width`, `effects`, …) or `key.field` for the nested objects `DesignJSON` merges field by field (`text.content`, `stroke.width`, `layout.spacing`, …), so overriding the text keeps the font following the main component. The instance root's `x` and `y` always belong to the instance and are never overrides.
- **Structure inside an instance belongs to the main component.** Inserting, deleting, moving, reordering, or pasting layers below an instance root is refused by `DesignDocument` with an error naming the instance, so the UI and the Agent share one rule; the UI disables those commands. A main component is never inside another main component or an instance, and an instance is never inside its own main component, directly or through nested instances.
- **Nested instances sync through the nearest main component.** An instance of B inside main component A is copied into every instance of A; the copy follows A's nested instance, which follows B, keeping overrides at each level. Toggle-visibility targets inside a main component are rewritten to the matching layers of each instance.
- **No file fails to open because of a component reference.** The format is version 10; versions 9 and older open unchanged. An instance whose main component is missing, is not one, would form a cycle, or does not match it one to one opens as detached layers; every other instance is fully synced on open. Paste repairs pasted layers the same way.
- **Deleting a main component detaches its instances in the same undo step; Cut does not.** Cut then Paste in the same document moves the main component under its id, and its instances follow it again.
- **Agent parity (ADR 0007).** `design_create_component`, `design_create_instance`, `design_list_components`, `design_reset_overrides`, and `design_detach_instance` call the same store methods as the Edit menu, the layers panel, the properties panel, and the Insert Component popover. `design_create_node` and `design_update_node` cannot set the component fields directly.

## Rejected Alternatives

- **Virtual instances**: an instance stores only its main component's id and its overrides, and every reader of the tree expands it on the fly. Files are smaller, but the renderer, `DesignIndex`, hit testing, layout, snapshots, the prototype window, HTML export, and the Agent's reads would all change, and ids for layers inside an instance would have to be invented and kept stable for selection and annotations. The App treats the document as a tree of concrete layers everywhere (ADR 0006), so materializing confines the feature to the editor and the panels.
- **Linked copies**: copy and paste records the original, and a "push changes" command rewrites copies on request. Cheap, but changes do not reach instances on their own, which is the point of the feature, and copies drift between pushes.
- **Recording overrides in each editing path**: every panel control, canvas gesture, and Agent tool would have to know whether it edits a layer inside an instance. Comparing old and new documents in one place covers every path, including ones added later.

## Consequences

- A project file stores every instance's layers in full, so a heavily reused component grows the file by its size per instance.
- Every edit pays for a walk over the subtrees it changed, and an edit to a main component rebuilds each of its instances; the benchmark keeps this in check.
- Instances cannot add, remove, or reorder their own layers; a variation in structure needs its own main component until variants exist.
- When an instance is detached while its main component is missing (the main component was cut and not pasted, and the file was saved and reopened), the instances of other main components nested in it are detached too: their links ran through the missing main component's layers, so they cannot be traced back to their own. This is accepted; Delete, which detaches while the main component is still there, keeps them as instances.
- Components shared between project files, libraries, and keeping component structure in HTML export remain out of scope; instances export as the layers they are.
