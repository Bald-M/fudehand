# Component Sets Store Variant Properties, and Switching Matches Layers by Name Path

2026-11-25 (#256, step 2). Status: **accepted**. The design is in the [variants spec](../superpowers/specs/2026-11-25-variants-design.md); it builds on [ADR 0014](0014-components-are-materialized-instances.md).

One component often comes in several versions: a button that is default, hovered, or disabled; a header that is light or dark. With step 1 each version was an unrelated main component, so an instance could not move from one to another without being replaced and losing its overrides. Fudehand now has **component sets**: a frame whose direct children are the **variants** of one component, each a main component described by a value for each of the set's **variant properties** (`State = Hover`). An instance of a variant switches to another variant of its set, keeping the overrides that still apply.

## Decisions

- **A component set is a frame marked with its property names; a variant stores its values.** Two fields join step 1's `ComponentFields` box, so layers outside components still pay one nil pointer: `componentSet: [String]?` on the set (its variant property names in display order) and `variant: [String: String]?` on each variant (a value for each of them). On disk they are `"componentSet": ["State"]` and `"variant": {"State": "Hover"}`, written only when set; the format is version 11, and versions 10 and older open unchanged. An instance of a variant is an ordinary step 1 instance whose `instance` is the variant's id; nothing new is stored on it, and its set is the variant's parent.
- **The set's rules are structural and checked in one place.** A component set is a frame that is not a main component or an instance and is not inside one, nor inside another set; its children are all variants, a variant's keys are exactly the set's properties, values are non-empty, and no two variants share all values. `DesignDocument` validates these on load (a broken rule is a load error, like any invalid field; instances of variants are still repaired as in step 1, so a variant reference never makes a file fail) and its `insert` and `move` refuse moving a layer into or out of a set with an error naming it, so the canvas, the panels, and the Agent share one rule. Reordering variants inside their set is allowed.
- **Combine as Variants is the only way existing main components enter a set.** It wraps main components sharing a parent in a new set at their union rectangle plus 16 points, keeping their ids, so their instances stay linked. Every other path makes a new variant with fresh ids — *Add Variant*, Duplicate of a variant, and pasting main components into a selected set — through one function (`ComponentVariants.insertVariant`), which places the copy 16 points below the variant it follows, grows the set, and makes the first property's value unique ("Hover" → "Hover 2" → "Hover 3"; a trailing number is continued when the value without it is used in the set). Any other layer is refused. A set is never where an inserted or pasted layer goes by default, and Create Component refuses a set or a layer holding one.
- **Switching rebuilds the instance from the new variant and pairs layers by name path.** `ComponentVariants.switchInstances` builds a fresh instance of the target variant with step 1's `makeInstance`, then walks the old and new trees together: the root keeps its id, position, and every override; below it, layers pair by name among siblings (same-named siblings first with first), and a paired layer takes back its old id — so its annotations and selection survive — and the overridden values that exist on the new layer. When a pair (or the root) differs in type, only overrides every layer type has are kept (name, visibility, lock, opacity, position, size, fill, stroke, sizing, interaction, states, animation). Nested instances pair only with instances of the same main component or of a variant of the same set. Unpaired layers are removed with their annotations, and toggle-visibility targets follow the kept ids and drop removed ones. Because the result is an ordinary, fully synced instance, step 1's reconcile, rendering, and undo need no change: a switch is one `perform`, one undo step.
- **The target variant is chosen by values, not by id.** Choosing a property value asks for the variant whose values equal the instance's current ones with that one changed; when none matches exactly, the variant with that value sharing the most other values (ties: first in set order). Switching several instances applies the same change to each from its own values. Only an instance's own root switches: a nested instance inside an instance follows its outer main component and is not offered the pop-ups.
- **Agent parity (ADR 0007).** `design_combine_as_variants`, `design_set_variant_properties`, `design_set_variant`, `design_add_variant`, and `design_switch_variant` call the same store methods as the Edit menu, the layers panel, and the properties panel; `design_create_instance` accepts a set id (its first variant); `design_list_components` reports each variant's `set` and `variant` and lists the sets. `design_create_node` and `design_update_node` cannot set `componentSet` or `variant`.

## Rejected Alternatives

- **Variants as override sets of one main component**: each variant would be a named bundle of overrides applied to a single main component. It cannot express variants that differ in structure (a disabled button with a lock icon), which is the main reason to have variants given that instances cannot change their own structure (ADR 0014).
- **Property values encoded in layer names (`State=Hover, Size=Small`)**, as Figma does: renaming a layer would silently break the variant, every reader (panels, Agent tools, validation) would have to parse names, and names are also what people and the switch's pairing read. Stored fields keep names free and make the rules checkable.

## Consequences

- Pairing by name path means renaming a layer in one variant but not another loses that layer's overrides on a switch; layers that should carry overrides across variants need the same names in each. This is the same contract Figma users know, and it is what makes structurally different variants possible.
- Overrides that only make sense on one layer type (text, auto layout, effects) are dropped when a switch pairs layers of different types; they cannot be carried silently onto a layer that does not have the property.
- Copying a whole set and pasting it in the same document gives a plain frame of instances, since each main component stays unique in a document (ADR 0014); pasting it into another document keeps it a set.
- A creation tool started inside a top-level set targets the set and is refused, like other inserts into a set.
- Documents without components pay only the walk added in step 1: the new fields live in the existing optional box, and no new pass runs on edit. Three paired runs of `pnpm bench:native` against the previous `main` put drag, hover, pan, edit, undo, selection, and open times for those documents within ±5% of it (5,100 layers: a drag event 1.54 → 1.57 ms, undo 3.01 → 2.80 ms; 16,046-layer open 146 → 147 ms). The one exception is the p95 GPU time of a frame at rest over 100 drawn frames, a small and noisy figure: 0.9–2.5 ms over six runs of `main` and 2.3–4.4 ms over six of this change; this change touches neither the renderer nor compositing.
- Boolean, text, and instance-swap component properties, variants shared between project files, and variants that switch by themselves in the prototype window (interactive components) remain out of scope.
